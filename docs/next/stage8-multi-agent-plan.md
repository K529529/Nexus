可以收口了。下面这份就是交给 Codex 的 **Nexus V0.3 Stage8 实施方案**：确定架构、行为边界、实施顺序和验收要求，具体代码组织、类型、参数和接口形式由 Codex 根据现有代码决定。

**1. 目标与开发约束**

Stage8 增加两项能力：

- **原生多 Agent 协作**：主 Agent 按需委派子代理，子代理复用 Nexus 核心循环。
- **运行中消息输入**：任务执行期间，用户可以引导当前任务，也可以排队提交下一任务。此能力同时适用于单 Agent 和多 Agent。

多 Agent 默认关闭。Stage8 的目标是建立可用、可观察、可比较的协作能力，收益由后续 ABK 对照实验验证，不预设它一定优于单 Agent。

开发要求：

- 从最新远端 V0.3 分支 `codex/nexus-v0.3` 创建独立分支，建议命名为 `codex/nexus-v0.3-stage8-multi-agent`。
- 开始时核对实际分支、基线提交和工作区状态，保护已有未提交修改。
- **按照下文阶段分别实现、验证、提交并推送，不能全部完成后一次性推送。**
- 本次已授权阶段性 commit 和 push；不自动合入 V0.3、不发布版本。
- 以当前 V0.3 代码和有效架构文档为基础，延续 Stage6 恢复机制、Stage7 可观测性，不重新搭建另一套运行时。

**2. 整体架构：原生 tool → subagent**

主 Agent 通过工具创建和管理子代理。是否委派、如何拆分任务、如何处理结果，由模型决定；运行时负责落实权限、并发额度、消息传递和生命周期。

主、子、孙 Agent 都复用同一套 Nexus Agent Loop：

- 使用相同的模型调用、工具执行、上下文管理和错误处理能力。
- 每个 Agent 拥有独立的会话、上下文、运行状态和日志。
- 使用同一 Python 进程中的独立 asyncio Task 并发执行。
- 模型请求、子进程等待等采用异步操作，不能让同步阻塞操作卡住整个事件循环。

**复用核心循环不等于共享会话对象。** 与会话绑定的工具、上下文、压缩状态、模型请求状态必须正确隔离；可以安全复用的连接等基础资源再共享。

增加轻量的运行管理职责即可，不引入 CrewAI、消息中间件，也不增加一个专门负责调度的模型。

多 Agent 配置放在 `config.toml`：

- 关闭时，模型看不到子代理工具，也不注入委派说明。
- 开启时，模型获得委派能力，但不要求每个任务都创建子代理。
- 运行时仍检查开关、权限和额度，不能只依赖工具是否出现在提示词中。

**3. 子代理上下文、角色与模型**

首版只实现 **Fresh 上下文**，不实现 Fork。

主 Agent 需要明确交代任务目标、必要背景、交付要求、约束和负责范围。子代理读取自己的角色说明、适用的项目规则以及任务说明，不自动复制父代理完整对话。

首版固定三个角色，分别提供内置 Markdown 角色文件：

| 角色 | 职责 | 默认推理强度 |
|---|---|---|
| scout | 探索代码、查找信息、整理事实与证据 | low |
| worker | 实现代码、修改文件、运行验证 | high |
| reviewer | 检查实现、验证行为、指出问题 | high |

模型默认继承主 Agent；用户可以在 `config.toml` 中覆盖各角色的模型和推理强度。创建时确定本次子代理的配置，主 Agent 后续切换模型不改变已经运行的子代理。

角色文件负责职责与行为约束，配置文件负责用户设置。首版不扩展自定义角色发现、角色市场或角色安装机制。

**4. 工具权限、Skills 与 MCP**

| 能力 | scout | worker | reviewer |
|---|---|---|---|
| Shell、读取与搜索项目 | 开放 | 开放 | 开放 |
| `apply_patch` | 不开放 | 开放 | 不开放 |
| 已启用的原生 Web Search | 开放 | 开放 | 开放 |
| Skills | 继承可用目录，独立加载 | 同左 | 同左 |
| MCP | 默认不开放，按角色显式配置 | 同左 | 同左 |

这里要明确：

- scout、reviewer 的“只读”属于职责约束。开放 Shell 后，不能声称具备硬性的文件系统只读隔离。
- 所有 Agent 继续经过现有安全、沙箱和审批机制，委派不能扩大权限。
- Skills 的可用目录可以继承，但加载状态和正文进入各自上下文，不能共享一个可变的会话加载状态。
- 子代理的 MCP 权限取父代理有效权限与角色配置的交集，孙代理同样遵守这一限制。

MCP 连接由根会话统一管理，各 Agent 的调用上下文、日志和工具封装独立。同一 MCP 服务首版串行调用，不同服务可以并发。子代理结束不能关闭其他 Agent 仍在使用的连接；服务失效需要同步反映到相关 Agent。

**5. 并发、嵌套委派与工作区**

主 Agent 为第 0 层，子代理第 1 层，孙代理第 2 层。

首版最大深度固定为 2，只提供 `allowNestedSubagents` 开关，不提供深度配置。嵌套关闭时，子代理不能继续委派；开启时遵守以下关系：

| 委派方 | 可以创建的角色 |
|---|---|
| 主 Agent | scout、worker、reviewer |
| worker | scout、worker、reviewer |
| scout | scout |
| reviewer | scout、reviewer |

第二层代理不再获得创建子代理的能力，运行时也必须检查深度。

同时存活的子代理默认最多 **3 个，可配置**：

- 子代理和孙代理共用额度，主 Agent 不计入。
- 等待回复、等待下级结果的代理仍占额度。
- 正在取消但尚未完成清理的代理仍占额度。
- 结束并清理完成后释放额度，日志继续保留。
- 额度满时立即返回明确状态，不建立隐藏的创建等待队列。父代理可以自行完成、等待已有任务结束或调整拆分。

工作区采用共享模式：

- 主、子、孙 Agent 使用同一个项目工作区。
- 主 Agent 划分文件修改范围，**同一时间同一文件只有一个执行者修改**，不同文件可以同时修改。
- 规则也约束主 Agent。委派出去的文件不能自己同时修改。
- worker 继续委派时，只能进一步拆分自己负责的范围，并让出对应文件的修改权。
- 不引入文件锁、自动 worktree、自动合并流程。

文件归属是明确的协作约定，不包装成强制隔离保证。最终集成验证应在相关修改稳定后进行；并发期间一次测试通过，不代表最终代码已经通过验证。

**6. 异步执行与父子通信**

创建子代理后，主 Agent 获得任务身份和状态，可以继续处理其他工作；需要结果时再等待。

这里区分两件事：

- **运行时允许并发**：子代理执行测试时，主 Agent 可以推进文档等其他任务。
- **模型选择等待**：主 Agent 如果暂时没有可推进的工作，可以主动等待子代理结果。

不能把“创建子代理”实现成默认一直阻塞到子代理结束，否则主 Agent 无法利用这段时间。

父子通信采用进程内异步消息机制：

- 父代理可以向直属子代理追加指导。
- 子代理可以汇报进度、提交结果或请求决策。
- 请求决策可以等待回复，普通进度通知不阻塞执行。
- 兄弟代理通过父代理协调，首版不建立任意 Agent 间的聊天网络。
- 父代理等待结果时，遇到子代理求助、用户引导、完成或失败等事件，应及时被唤醒。

等待结果设有限时：

> 等待超时只返回当前状态，子代理继续执行。它不等于子代理执行超时，也不触发重启。

消息在安全的模型请求边界进入上下文。普通指导不强制打断正在执行的工具，不能破坏工具调用与工具结果的完整配对。

**7. 失败、取消与恢复**

需要明确区分：

- 测试失败、命令非零退出等属于工具结果，由 Agent 根据结果继续处理。
- 无法恢复的模型或运行时错误，才使该代理进入失败状态。
- 一个子代理失败，不自动取消其他兄弟代理；父代理决定接管、恢复或重新委派。
- 运行时不自动重放整个失败任务。

取消沿代理树向下传播。取消完成必须包含所属工具子进程的清理；清理失败应明确显示，不能提前宣布结束、释放额度或交回修改范围。

主 Agent 正常结束前，需要收回相关结果，或明确取消并清理剩余代理。首版不支持主任务结束后留下无人管理的后台代理。

恢复继续沿用 Stage6 原则：

- 恢复根会话时，重建代理关系、已完成结果和中断状态。
- 已完成并交付的结果不重复注入；完成但尚未交付的结果可以补交。
- 未完成代理标记为中断，不自动恢复整棵代理树。
- 父代理可以显式恢复某个子代理，使用该子代理自己的历史继续执行。
- 不重放已经执行的命令，不把副作用未知当作未执行。
- 不能通过另建子代理绕过工作区内尚未核实的副作用。
- 恢复时重新检查当前权限，不恢复历史的一次性审批。

恢复的是任务和会话状态，不是旧进程中的 asyncio Task。

**8. 运行中输入与多 Agent TUI**

运行中输入作为通用能力实现，关闭多 Agent 后仍然可用。

| 状态 | Enter | Tab |
|---|---|---|
| 空闲 | 提交新任务 | 保留补全行为 |
| 任务执行中 | 引导当前任务 | 排队为后续任务 |

补全菜单正在操作时，优先完成补全交互；多行输入、粘贴和审批输入不能被这些快捷键破坏。

交互要求：

- 输入后立即显示已接收，区分“已收到”和“已交给模型”。
- 引导在下一个安全边界交给当前 Agent，不自动替换原任务。
- 用户问一句问题时，Agent 可以先回答，再继续原任务。
- 排队消息在当前任务结束后执行，尚未投递的消息支持查看、修改或撤回。
- 默认发送给主 Agent；用户显式选择某个子代理时，可以向它发送指导，并让父代理获知。
- 不默认广播给全部代理。

多 Agent TUI 在 Nexus 现有风格上增加代理树和详情：

- 显示角色、任务摘要、状态、当前操作、耗时和用量。
- 孙代理按层级展示。
- 主区域保持主 Agent 输出；子代理详细过程按需展开，不把所有流混在一起。
- 子代理求助、失败和等待用户决策要明显可见。
- 执行期间输入框保持响应，审批弹窗明确接管输入。

真实手感由 Archer 在 Windows 终端验收；实现不能只完成静态展示。

**9. JSONL、history、HTML trace 与遥测**

保留主会话现有 JSONL，增加按主会话归属的子代理目录：

```text
<session_id>.jsonl
<session_id>/subagents/<agent_id>.jsonl
```

每个代理实例一份日志，孙代理也独立记录，通过关系信息恢复层级。同一个角色多次创建时不能共用日志文件。

主日志记录委派、通信和结果摘要；子日志记录自己的完整执行过程，避免把全部子日志再复制进主日志。

同步更新现有展示入口：

| 入口 | Stage8 展示要求 |
|---|---|
| TUI | 实时代理树、状态、消息与用量 |
| history | 主会话下查看子代理概况和各自轨迹 |
| HTML trace | 代理树、按代理筛选、并行时间线、等待与通信关系 |
| 现有遥测 | 同一次任务执行中的父子关联、模型调用与工具调用 |

子代理不挤占普通 history 顶层会话列表。旧日志和单 Agent 会话继续正常显示，不出现无意义的空面板。

沿用 Stage7 的日志投影和导出机制：

- 一次根任务执行关联整棵代理树。
- 创建子代理的工具调用与子代理完整生命周期分别记录。
- 恢复执行使用新的执行轨迹并关联原任务，不伪造跨进程停机期间的运行时长。
- 导出失败不影响本地结果。
- 遥测继续遵守既有内容边界，不新增上传提示词、源码或完整工具正文。

用量统一口径：

- 每个 Agent 只计算自己的实际请求，再汇总整棵树。
- 失败、取消、压缩及已报告用量的重试请求均计入。
- 缓存用量、推理用量按 Provider 语义处理，不能重复相加。
- 未知用量明确标识，不当作零。
- 日志重放、结果转交和导出不产生新的用量记录。
- 总耗时使用实际经过时间，不累加各代理并行耗时。
- 无可靠价格时不伪报费用。

TUI、history、HTML 和后续 ABK 统计使用同一事实来源。

**10. 分阶段开发与推送**

按以下顺序推进，每阶段都有可验证的交付。阶段内部可以有多个提交，但**阶段结束必须完成一次推送和进度报告**。

| 阶段 | 交付内容 | 本阶段重点验收 |
|---|---|---|
| Stage8-1：通用运行中输入 | 输入与执行解耦，Enter 引导、Tab 排队，待处理消息展示 | 单 Agent 执行期间输入有效；原任务持续；工具协议完整 |
| Stage8-2：原生子代理闭环 | 配置开关、三个角色、Fresh、独立会话、异步创建、结果获取、子日志 | 默认关闭无影响；父子复用同一循环；真实并发且上下文不串 |
| Stage8-3：协作与资源管理 | 父子消息、嵌套委派、全树额度、工具权限、Skills/MCP 继承、取消清理 | 孙代理计入额度；满额及时返回；求助不死锁；权限不扩大 |
| Stage8-4：持久化与恢复 | 中断识别、结果补交与去重、子代理显式恢复、Stage6 衔接 | 不重复创建、不重复执行副作用、不丢已完成结果 |
| Stage8-5：终端体验 | 完整代理树、详情、选定代理指导、求助和失败提示 | 输入、渲染、审批互不干扰；Windows 实际交互可验 |
| Stage8-6：历史与可观测性 | history、HTML trace、遥测关联、全树用量 | 各入口状态与统计一致；旧日志兼容；费用不重计 |
| Stage8-7：集成与交付 | 全量回归、跨平台 smoke、文档与配置说明、ABK 对照准备 | 单 Agent 无回归，多 Agent 行为闭环，证据完整 |

每阶段向用户报告：

- 实际完成的能力。
- 验证结果及尚未验证的部分。
- 提交与远端推送情况。
- 下一阶段内容和已知问题。

通过阶段验证后继续推进，不需要每阶段重新请求常规实施许可。遇到必须改变已定架构的情况，再提出具体冲突和建议。

**11. 验收与 ABK 对照**

确定性测试重点覆盖以下行为：

- 多 Agent 关闭时，工具、提示词和执行行为保持正确。
- 父子独立推进，没有共享会话污染或同步阻塞。
- 嵌套深度、角色委派关系、全树额度生效。
- 满额、求助和等待结果不会形成死锁。
- 引导与排队在正确边界生效。
- 取消确实清理真实子进程，不仅测试模拟对象。
- 崩溃恢复不重放副作用，结果不会重复交付。
- 日志、history、HTML 和遥测的关系与用量一致。

按照仓库当前要求完成格式、类型、测试、构建和安装验证。缺少平台或真实模型环境时，如实记录未验证，不能用替身测试冒充真实体验验收。

最终真实体验至少验证：

1. 单 Agent 执行中接受引导，并继续原任务。
2. 子代理测试期间，主 Agent 推进另一项工作。
3. 两个 worker 修改不同文件，主 Agent 汇总并完成集成验证。
4. 子代理请求决策、用户指导、取消和恢复形成完整闭环。

之后使用 ABK 比较多 Agent 开启与关闭：

- 相同任务、代码基线、环境和主模型设置。
- 记录子代理实际模型与推理强度。
- 对比通过率、耗时、全树 token、费用和失败类型。
- 区分“开启了能力”和“模型实际使用了委派”。
- 能力正确性与 benchmark 收益分别报告，不把多 Agent 更快或更省作为必然结论。

**交付给 Codex 的核心要求就是：按上述边界实现原生协作，保持一套核心循环，分阶段验证、提交和推送；最终交付可运行、可追踪、可对照评测的 Stage8 分支，等待人工体验验收与合入。**
